## Product design

### Goals / Non-goals

**Goals:**
- Give Agent-platform clients a single MCP connector, `epicor-kinetic-mcp`, that lets an AI agent discover a tenant's Epicor Kinetic data model (catalogs/schemas/tables/columns) and run read queries against it, using credentials the tenant already has in their own CData Connect AI account.
- Every call is per-tenant: credentials arrive on each request (via the Gateway), nothing is shared across tenants, and nothing is cached between calls — matching the "credentials encrypted and every action logged" promise in the ticket.
- Match the platform's generic MCP conventions (tool naming, pagination, structured errors) so this connector behaves like every other connector already live on the Gateway.

**Non-goals (v1):**
- Writing to Epicor Kinetic (creating/updating rows, running stored procedures) is out of scope for v1. The ticket does not name a specific write use case, and SOP §2.7 ("Write/Delete tool admission") says not to add write tools without an explicit business need on multi-tenant production ERP data — Epicor Kinetic procedures in particular can post real financial/production transactions. See "Decisions made by DEV01" below.
- Provisioning or configuring the tenant's CData Connect AI account, or the Epicor Kinetic connection inside it, is out of scope — that is a prerequisite the tenant (or whoever sells them the connector) sets up directly with CData, the same way the ticket's own Conduit listing assumes.
- Implementing Epicor Kinetic's native REST API directly is out of scope (no public spec to build against — see Current state).

### Acceptance criteria AC1..AC8

- **AC1 — Tool surface.** Given a client calls `tools/list` on `epicor-kinetic-mcp`, when the server responds, then it returns exactly the v1 tool set — `epicor_search_context`, `epicor_list_catalogs`, `epicor_list_schemas`, `epicor_list_tables`, `epicor_list_columns`, `epicor_query_data`, `epicor_get_started` — every tool prefixed `epicor_`, and no tool named or shaped like an insert/update/procedure-execution operation.
- **AC2 — Missing credentials.** Given a `/mcp` request is missing `X-Epicor-Email` or `X-Epicor-Pat` (or both), when the server receives it, then it returns `401` listing the missing header name(s), and no call reaches CData Connect AI.
- **AC3 — Read query.** Given valid credentials, when a client calls `epicor_query_data` with a `SELECT` statement, then the server returns the rows as compact JSON (not CData's raw CSV), capped at `limit` (default 50, hard max 200) and at 20,000 characters, with `has_more` set when either cap truncates the result.
- **AC4 — Schema discovery.** Given valid credentials, when a client calls `epicor_list_catalogs` / `epicor_list_schemas` / `epicor_list_tables` / `epicor_list_columns`, then each returns the catalogs/schemas/tables/columns visible through the tenant's CData Connect AI connection, trimmed to the fields an agent needs (name, type, parent) rather than CData's full metadata payload.
- **AC5 — Natural-language discovery.** Given valid credentials, when a client calls `epicor_search_context` with a natural-language question, then the server returns the candidate datasets/fields CData's own `search_context` tool identifies as relevant.
- **AC6 — Onboarding.** Given valid credentials, when a client calls `epicor_get_started`, then the server returns the combined onboarding and connector-specific guidance text (CData's `getStarted` + `getInstructions`).
- **AC7 — Structured errors.** Given CData Connect AI returns an auth failure, an invalid-SQL / bad-argument error, a rate limit, or an upstream failure, when the tool call completes, then the response is the standard envelope `{"error": {"code", "message", "retryable"}}` with `code` one of `unauthorized` / `invalid_argument` / `rate_limited` (`retryable=true`) / `upstream_error` (`retryable=true`), never a raw exception.
- **AC8 — Tenant isolation.** Given two concurrent requests carry different `X-Epicor-Email` / `X-Epicor-Pat` pairs, when both are in flight at the same time, then each reaches CData Connect AI with its own Basic-auth header and neither response or error can be attributed to the other tenant's credentials.

### Open questions

- Should write tools (insert/update rows, run stored procedures) be added in a later version? **Not blocking** — v1 ships read-only per the "Decisions made by DEV01" rationale below; if a concrete write use case exists, describe it in a follow-up ticket (new AC + updated tool list), which will also need its own destructive-tool review (SOP §2.7).
- Does MSPbots provision the tenant's CData Connect AI account/PAT, or does the tenant bring their own? **Not blocking the design** — architecturally identical either way (credentials just arrive as headers); documented in the README's "where to get these credentials" column as "your organization's CData Connect AI account," which matches how the ticket's own Conduit listing frames it (the client connects their own vendor account).

## Tech design

### Conclusion

Build `epicor-kinetic-mcp` as a thin, stateless MCP proxy (Python 3.12 + FastMCP, per the SOP's recommended stack) that holds no Epicor-specific logic of its own: each tool call is translated into one JSON-RPC `tools/call` request to CData Connect AI's hosted MCP endpoint (`https://mcp.cloud.cdata.com/mcp`), authenticated with the tenant's own `email:PAT` taken from that request's headers, with the response reshaped to fit this platform's pagination/error/naming conventions. v1 exposes 7 read-only tools (see AC1); no write or procedure-execution tools are built.

### Where the current implementation lives

Nowhere yet — `MSPbotsAIFramework/epicor-kinetic-mcp@main` (07468bd) is an empty scaffold (`README.md:1-2` only). Everything in this section is new code.

### Option analysis

1. **Thin proxy to CData Connect AI's hosted MCP endpoint (chosen).** CData already solves "turn Epicor Kinetic's tenant-specific login and data model into a generic queryable SQL surface" — that is exactly the gap that makes Epicor Kinetic unbuildable directly (see Current state). Proxying reuses that work, keeps this repo small (no Epicor-specific SQL dialect or auth flow to maintain), and matches the mechanism the ticket itself names. Trade-off: the connector depends on CData Connect AI staying up and on the tenant having both a CData Connect AI account *and* an Epicor Kinetic connection configured inside it — a dependency outside this repo's control, which is called out in Risks & dependencies.
2. **Direct Epicor Kinetic REST client (rejected).** Epicor Kinetic's REST API (`Erp.BO.*` business objects) is real and documented, but only inside each tenant's own per-instance Help site behind that tenant's login — there is no single public spec to implement against, which conflicts with the "implement from the vendor's official public API docs" rule for new MCP builds (`references/mcp-track.md` §2.2 step 0). Per-tenant onboarding would also require capturing each tenant's Kinetic base URL and a Kinetic-specific OAuth/API-key flow we cannot test without a live tenant, with no generic win over option 1.
3. **No new MSPbots-hosted connector; tell the client to point their AI client at CData Connect AI's own MCP URL directly (rejected).** This throws away the thing the ticket is actually asking for: a connector that is *visible, controlled, and audited through the Agent platform's Gateway* the way every other MSPbots connector is. It also does not match "Connect it [through MSPbots]" in the ticket's own wording.

### Data & API contract

**Transport:** `POST /mcp` (MCP Streamable HTTP, `stateless_http=True`); `GET /health` → `{"status": "ok"}`, purely local (SOP §1.1).

**Credentials (request headers):**

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Epicor-Email` | Yes | The email address used to sign in to your organization's CData Connect AI account | Your CData Connect AI account |
| `X-Epicor-Pat` | Yes | Personal Access Token generated on CData Connect AI's Personal Access Tokens page | CData Connect AI → Settings → Personal Access Tokens |
| `X-Epicor-Base-Url` | No | Override for CData Connect AI's MCP endpoint; default `https://mcp.cloud.cdata.com/mcp` | — (only needed for a non-default CData deployment) |

Requests are authenticated upstream with HTTP Basic `<email>:<PAT>`, matching CData Connect AI's own documented auth model. A `/mcp` request missing `X-Epicor-Email` or `X-Epicor-Pat` gets `401` listing the missing header(s) before any upstream call is made (SOP §3.2).

**Upstream call shape** (to `X-Epicor-Base-Url`, default CData's hosted endpoint):

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "queryData", "arguments": {"query": "SELECT TOP 50 * FROM Customer"}}}
```

**Tool list (v1, 7 tools, all read-only — well under the SOP §2.1 guideline of ≤20):**

| Tool | Proxies (CData tool) | Notes |
|---|---|---|
| `epicor_search_context(question: str)` | `search_context` | Natural-language dataset/field discovery |
| `epicor_list_catalogs()` | `getCatalogs` | |
| `epicor_list_schemas(catalog: str \| None)` | `getSchemas` | |
| `epicor_list_tables(catalog: str \| None, schema: str \| None)` | `getTables` | |
| `epicor_list_columns(table: str)` | `getColumns` | |
| `epicor_query_data(sql: str, limit: int = 50)` | `queryData` | `SELECT`-only (enforced upstream by CData); `limit` capped at 200; 20,000-char truncation with `has_more` |
| `epicor_get_started()` | `getStarted` + `getInstructions` (combined) | Onboarding + connector-specific guidance |

No `epicor_insert_rows` / `epicor_update_rows` / `epicor_run_procedure` in v1 — see "Decisions made by DEV01."

**Error envelope** (SOP §4.2), mapped from CData's JSON-RPC error / the underlying HTTP status:

| CData / upstream condition | `code` | `retryable` |
|---|---|---|
| HTTP 401/403, or a JSON-RPC auth error | `unauthorized` | false |
| HTTP 400/422, invalid SQL, bad argument | `invalid_argument` | false |
| HTTP 429 | `rate_limited` | true |
| HTTP 5xx, connection error, timeout | `upstream_error` | true |

There is no by-ID "get a single resource" tool in v1, so `not_found` is not expected to occur; it is reserved in the shared vocabulary for a future tool that needs it. An empty `queryData` result set is a normal empty result, not an error (SOP §4.2).

**No database / migration** — this service holds no data of its own; it is a stateless proxy.

### Key flow / sequence

1. Gateway → `POST /mcp` with `X-Epicor-Email` / `X-Epicor-Pat` (and optionally `X-Epicor-Base-Url`) plus the MCP JSON-RPC body.
2. Middleware checks both required headers are present; missing either → `401` immediately, no upstream call (AC2).
3. Middleware stores the credential pair in a `ContextVar`, cleared in `finally` once the response is built (AC8).
4. The matched tool handler builds the corresponding CData `tools/call` request and calls `api_client.call_tool(...)`, which applies the 5s/30s connect/read timeouts and retries 429/5xx with backoff (Retry-After honored).
5. CData's response is reshaped: `queryData`'s CSV → compact JSON rows (limit/char-cap/`has_more` applied); discovery responses trimmed to name/type/parent; errors mapped per the table above.
6. Response returned as a JSON string (success body or the `{"error": ...}` envelope) — never a raised exception out of the tool layer (SOP §4.1).

### Non-functional

- **Idempotency/concurrency:** all v1 tools are reads; `epicor_query_data` is additionally marked `idempotentHint=True`. There are no write tools in v1, so the "retry duplicates a write" risk the SOP flags for `insert`/`execute_procedure` does not apply yet — it will need explicit handling if write tools are added later (see Open questions).
- **Performance:** single tool call (including retries) stays under the SOP's 120s ceiling; `epicor_query_data` and discovery tools apply the §2.5 result-size caps so a large Epicor dataset cannot blow up one response.
- **Security:** credentials arrive only via headers, are never written to config/env/disk, and are scoped to a single request's `ContextVar` (SOP §3.1/§3.3); no credential, token, or CData response body is ever logged (SOP §6).
- **Multi-tenant isolation:** each request builds its own Basic-auth header from its own headers; the shared `httpx.AsyncClient` carries no baked-in auth or cached tenant data, so connection pooling cannot leak credentials or results across tenants (AC8, SOP §3.3/§3.4).
- **Logging/observability:** structured logs (tool name, request id, CData HTTP status, latency, mapped error `code`) — no header values, no query text with potentially sensitive data beyond what SOP §6 permits.

### Risks & dependencies

- **No live CData Connect AI / Epicor Kinetic account available to DEV01.** All tool logic is validated against mocked CData responses; the manual "needs a real vendor account" test cases (AC3/AC4) are the only way to confirm the real response shapes match what was designed here. Not a blocker per `references/mcp-track.md` §2.5, but it is the main source of risk this design carries into the dev leg.
- **Hard dependency on a third-party SaaS the tenant must separately own and configure** (a CData Connect AI account with an Epicor Kinetic connection already set up inside it). If that connection is missing or misconfigured, CData will return a technically valid response with no Epicor tables in it — this connector cannot detect or distinguish that from "the tenant genuinely has no tables," since it has no independent knowledge of what Epicor Kinetic should contain. Documented in the README so the failure mode is visible, not silently mysterious.
- **CData's documented API was read through a page-summarization fetch of `https://docs.cloud.cdata.com/en/API/MCP`, not the raw spec/OpenAPI file** (none was found linked from that page). If CData's actual JSON-RPC parameter names differ in some detail from what the summarized page states, the dev leg will need to adjust `api_client.py` against the real endpoint — flagged here rather than silently assumed correct.
- No dependency on another not-yet-merged ticket, and no network/gateway change required beyond standard MCP registration.

## Decisions made by DEV01

- **Proxy to CData Connect AI instead of building a direct Epicor Kinetic REST client.** Why: Epicor Kinetic has no single public API spec (per-tenant-hosted docs); CData Connect AI does, and is the mechanism the ticket's own Conduit link names. Alternative not chosen: direct Epicor REST integration (rejected — no public spec, see Option analysis #2).
- **v1 is read-only; no insert/update/procedure-execution tools.** Why: the ticket does not name a specific write use case, and SOP §2.7 says not to add write tools to multi-tenant production ERP data without one — Epicor Kinetic procedures can post real financial/production transactions. Alternative not chosen: expose CData's `execute_insert`/`execute_update`/`executeProcedure` 1:1 in v1 (rejected — no stated need, higher risk, can be added later behind its own review if requested).
- **Discovery kept as four separate granular tools (`list_catalogs`/`list_schemas`/`list_tables`/`list_columns`) instead of one combined "discover" tool.** Why: mirrors CData's own hierarchy so an agent can drill down progressively with small, specific calls, and keeps each tool's `description`/parameters short (SOP §2.2 ≤500 chars). Alternative not chosen: a single `epicor_discover(level, parent)` tool (rejected — would blur each call's filter semantics and make the parameter documentation harder to keep concise).
- **`getStarted` and `getInstructions` merged into one `epicor_get_started` tool.** Why: both are onboarding/guidance text with overlapping purpose per CData's own docs; keeping them separate would add a tool that rarely gets called on its own. Alternative not chosen: two separate tools (rejected — marginal value, adds to the tool count for no decision-relevant benefit to the agent).
- **Header prefix is `X-Epicor-*`, not `X-Cdata-*`, even though the credential is a CData Connect AI account.** Why: the connector is catalogued and named for Epicor Kinetic (matching the ticket, the repo name, and the tool name prefix); the README's "where to get it" column spells out that the credential actually comes from the tenant's CData Connect AI account, so this is not misleading. Alternative not chosen: `X-Cdata-*` headers (rejected — would be inconsistent with the `epicor_` tool prefix and the repo's own name).
- **`X-Epicor-Base-Url` included as an optional header even though CData currently has one public endpoint.** Why: forward-compatible with a future region-specific or dedicated CData deployment, at zero cost (defaults to today's one known endpoint). Alternative not chosen: hardcode the URL with no override (rejected — cheap to avoid, and other connectors in this org follow the same optional-base-URL pattern for similarly single-endpoint vendors).

To change any of these, say so in a comment and move this ticket back to `5b - ready for groom`.

- **TC-EPICOR-001 (AC1):** `tools/list` returns exactly the 7 documented `epicor_`-prefixed tools, no insert/update/procedure-execution tool present.
- **TC-EPICOR-002 (AC2):** `/mcp` with neither credential header set returns `401` listing both `X-Epicor-Email` and `X-Epicor-Pat`.
- **TC-EPICOR-003 (AC2):** `/mcp` with `X-Epicor-Email` set but `X-Epicor-Pat` missing returns `401` listing the missing header.
- **TC-EPICOR-004 (AC3):** `epicor_query_data` with a `SELECT` and no explicit `limit` returns rows as JSON, defaulting to `limit=50`, under 20,000 characters.
- **TC-EPICOR-005 (AC3):** `epicor_query_data` against a mocked CData response larger than 20,000 characters is truncated with `has_more=true`.
- **TC-EPICOR-006 (AC3, needs a real vendor account):** the same query against a live CData Connect AI + Epicor Kinetic tenant returns real Epicor rows in the same shape the mocked test expects.
- **TC-EPICOR-007 (AC4):** `epicor_list_catalogs`/`epicor_list_schemas`/`epicor_list_tables`/`epicor_list_columns` map a mocked CData response into the trimmed (name/type/parent) shape.
- **TC-EPICOR-008 (AC4, needs a real vendor account):** the same discovery tools against a live tenant return that tenant's actual Epicor Kinetic catalog/schema/table/column names.
- **TC-EPICOR-009 (AC5):** `epicor_search_context("open sales orders")` returns the candidate datasets a mocked CData `search_context` response lists.
- **TC-EPICOR-010 (AC6):** `epicor_get_started` returns non-empty combined text from both mocked CData `getStarted` and `getInstructions` responses.
- **TC-EPICOR-011 (AC7):** mocked CData 401/403 → `unauthorized`; 400/422 → `invalid_argument`; 429 → `rate_limited` (`retryable=true`); 5xx/timeout → `upstream_error` (`retryable=true`) — never a raised exception.
- **TC-EPICOR-012 (AC8):** two concurrent requests with different `X-Epicor-Email`/`X-Epicor-Pat` pairs each reach the mocked CData transport with their own Basic-auth header; neither request's captured outgoing header matches the other's credentials.
